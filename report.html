1. Executive Summary

The Support Desk System is an end-to-end customer support operations application engineered to satisfy all core criteria, technical expectations, and UI/UX standards outlined in the Candidate Practical Assessment Brief. The system provides support agents and administrators with comprehensive capabilities to capture customer tickets, organize triage, manage assignments, log audit trails, add public replies and internal notes, apply multi-criteria search and filters, and evaluate support desk performance via a live, database-calculated dashboard.

Unlike prototype demonstrations that mock APIs or fabricate dashboard numbers in local state, this application works completely end-to-end: Frontend (React 19 + TypeScript + Tailwind) → REST API (Express 5 + TypeScript) → Prisma ORM 6 → Relational Database (SQLite / PostgreSQL-ready). Every state change is persisted, every dashboard metric is computed by SQL aggregate queries, and every ticket action records an audit trail.

4. Core Business Rules & Implementation

A. Dynamic 24-Hour Overdue Rule

Overdue Definition: A ticket is overdue if and only if status !== 'RESOLVED' and createdAt < (now - 24 hours).

Implementation Decision: Overdue status is never stored as a boolean column in the database. Storing a boolean creates stale data unless a cron job continually re-scans the table. Instead, our service calculates overdue status dynamically in SQL queries: 

const twentyFourHoursAgo = new Date(Date.now() - 24 * 60 * 60 * 1000);
const overdueCount = await prisma.ticket.count({
  where: {
    status: { not: 'RESOLVED' },
    createdAt: { lt: twentyFourHoursAgo },
  },
});

When a ticket is marked Resolved, it instantly ceases to be overdue on both the client UI and the dashboard counters.

B. Atomic Audit Trail Generation

Whenever a ticket is created or updated, mutations are wrapped in prisma.$transaction(). Changes to status, priority, or assigneeId generate precise audit records containing old and new values:

Trigger Event Action Code Recorded Metadata
Ticket Creation CREATED Performed by system/user; timestamp.
Status Modified STATUS_CHANGED field: "status", oldValue: "OPEN", newValue: "IN_PROGRESS"
Priority Modified PRIORITY_CHANGED field: "priority", oldValue: "MEDIUM", newValue: "URGENT"
Assignee Assigned/Reassigned ASSIGNED field: "assignee", oldValue: "Sarah Chen", newValue: "James Wilson"
Public Reply Added COMMENT_ADDED Performed by author; updates ticket's updatedAt.
Internal Note Added NOTE_ADDED Performed by author; updates ticket's updatedAt.

C. Public Replies vs. Internal Notes Visual Distinction

To eliminate the risk of support agents accidentally publishing internal team discussions to customers:

  • Public Reply: Displayed in a neutral slate card with a subtle "Public Reply" label.
  • Internal Note: Highlighted in a vibrant amber container with an internal note lock badge (Internal Note). The entry textarea also shifts to an amber tint when the note mode is toggled.

9. Technical Decisions & Interview Defense

  1. Why Prisma with SQLite (PostgreSQL Ready)?

    In an assessment setting, friction during local evaluation is a primary failure mode. Requiring reviewers to install Docker, start PostgreSQL daemon services, and configure local role credentials introduces failure vectors. SQLite provides self-contained zero-config execution while retaining full relational semantics (foreign keys, cascading rules, unique indexes). Switching to PostgreSQL requires updating only a single line in schema.prisma.

  2. Why Atomic Transactions for Activity Logging?

    If an application updates a ticket status but the subsequent activity log insertion fails, the system enters an inconsistent state where audit history cannot be trusted. By wrapping both operations in prisma.$transaction(), both succeed or fail together atomically.

  3. Why Compute Overdue at Query Time?

    A persistent is_overdue column in the database is an anti-pattern because elapsed time changes continuously without write operations. Computing overdue via status != 'RESOLVED' AND createdAt < (now - 24h) ensures 100% time accuracy with zero background synchronization overhead.
